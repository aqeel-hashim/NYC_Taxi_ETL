# ADR-0007: OIDC Authentication with Dex and oauth2-proxy

## Status

Accepted.

## Context

The local platform exposes multiple web UIs (Airflow, Grafana, MinIO console, Streamlit, Mailpit, webhook receiver, Prometheus). Each has its own auth mechanism or none at all. A unified identity layer avoids managing separate credentials per service and mirrors production OIDC patterns.

## Decision

Use **Dex** as the OIDC identity provider and **oauth2-proxy** (via Traefik ForwardAuth) for services without native OIDC support.

- Dex stores generated admin and viewer user credentials (static passwords for local dev).
- Airflow, Grafana, and MinIO use native OIDC integration with Dex.
- Streamlit, Mailpit, Prometheus, and webhook UI are protected by oauth2-proxy ForwardAuth through Traefik.
- Group claims from Dex map to Airflow roles (admin/viewer).
- TLS certificates generated by `mkcert` with SANs for all `*.taxi.localhost` hostnames.
- CoreDNS rewrites internal hostnames to Traefik ClusterIP for consistent OIDC issuer URL inside/outside cluster.

## Alternatives Considered

- **Keycloak**: Heavier resource footprint. Dex is lighter for local dev with a small fixed user set.
- **No auth**: Unacceptable for a platform with multiple services and role-based access.
- **Basic auth per service**: Fragmented, hard to manage, no group mapping.

## Consequences

- Adds Dex and oauth2-proxy deployments to the cluster.
- TLS setup requires `mkcert` CA installation on the host.
- WSL2 requires separate Windows browser trust configuration.
- OIDC issuer must resolve identically inside and outside the cluster (CoreDNS mapping).
- Degraded setup is documented when host refuses CA installation.
